# Phase 0 Research: Fix UX Bugs and Unify Story Bible

**Feature**: 012-fix-ux-unify-bible
**Date**: 2026-04-17

No `[NEEDS CLARIFICATION]` markers remained in the spec after `/speckit.clarify`. The items below are the implementation-level questions that still need a reasoned answer before writing code. Each is recorded as **Decision / Rationale / Alternatives considered**.

---

## R1 — Where does `ChapterGenerator` read characters/facts/locations from?

**Decision**: `ChapterGenerator` reads through `Eidos::StoryBible` (which already wraps the pluggable storage backend). The `#load_world_data` / `#load_story_facts` / `#build_character_sheet` helpers that today read `data/world.yml` and `data/story_facts.yml` are replaced by calls into the already-loaded `StoryBible` instance owned by the world.

**Rationale**: `StoryBible` is the canonical engine class; it already knows how to enumerate characters, locations, facts, relationships, and plot threads. The SDK (`Eidos::World#bible`) exposes the same object. Routing the producer through it closes the dual-store loop with one consistent code path and aligns with Constitution Principle IV (Canon Integrity).

**Alternatives considered**:
- *Port the legacy YAML readers into the StoryBible format internally.* Rejected: keeps the parallel schema alive in code, just hidden. Doesn't actually fix the architectural split.
- *Add a thin compat shim that reads both stores.* Rejected by the clarification Q3 answer — Eidos only supports the new layout.

---

## R2 — What about `story_bible_exporter.rb` still writing `data/world.yml` and `data/story_facts.yml`?

**Decision**: Keep `StoryBibleExporter` as-is. Its target is the **Jekyll site's** `_data` directory, not the world's canonical `data/` directory. That output IS the publishing-layer contract with Jekyll templates and must not change without a site rebuild.

**Rationale**: Constitution VII separates Engine from Publishing. The exporter lives on the publishing boundary — it translates canon state into whatever format the publishing target expects. Jekyll templates already expect `world.yml` and `story_facts.yml` under the site's data directory. Changing that belongs to a future "Jekyll site refactor" feature, not this one.

**Alternatives considered**:
- *Delete the exporter entirely and teach Jekyll to consume `data/story_bible/` directly.* Out of scope and unnecessary — the exporter is a clean derivative path.

---

## R3 — How are `CHARACTER_NAME` / `CHARACTER_DESCRIPTION` placeholder warnings eliminated?

**Decision**: In `prompt_utils.rb`, when a character section would be interpolated but the bible has zero characters, **omit the section entirely** from the prompt and return the template with the `{{CHARACTERS}}` block (or equivalent) removed. Do not emit a warning in that case.

Warnings remain for placeholders that are left unresolved for unrelated reasons (e.g. typo in a template), but not for the intentionally-empty case.

**Rationale**: The current behavior interpolates literal `CHARACTER_NAME` strings into the prompt and warns. Both are noise. An empty bible is a legitimate state (fresh world), and the fix is "compose a prompt that doesn't need a characters section" rather than "inject a placeholder".

**Alternatives considered**:
- *Replace placeholders with coherent fallback text ("no characters yet").* Rejected: adds surface area to maintain and could confuse the LLM into inventing characters anyway. Omitting is simpler.
- *Keep the literal tokens but swallow the warning.* Rejected: the literal token ends up in the generated chapter, which is the bug users see.

## R4 — How does the chapter get a substantive title (no "Chapter N" placeholder)?

**Decision**: Extend the chapter-generation prompt to require the LLM to return a title in its structured output (already JSON-style). Parse `title` from the response and use it as the chapter's title; fall back to `"Chapter #{N}"` only if the LLM fails to emit one. Strip "Not specified" from displayed metadata.

**Rationale**: Titles generated by the LLM for the specific chapter content are always better than a hardcoded "Chapter 1". The structured-output path already exists in `ChapterGenerator`; adding one field is low-risk.

**Alternatives considered**:
- *Derive the title from the first heading of the body.* Rejected: the body's first heading is not guaranteed; requires post-processing.
- *Have Eidos synthesize a title from the premise without an LLM call.* Rejected: a second-hand title disconnected from the actual chapter content is worse than no title.

---

## R5 — Interactive default alignment in `cli/world.rb`

**Decision**: For every interactive prompt that offers a default plus a list of options, ensure the default is a member of the list. Where the current defaults ("fiction", "narrative") are not in the lists, change the **default** to match an option (e.g. first entry), not the other way around. When a prompt genuinely accepts free-form input, render it as a plain prompt with no options table.

**Rationale**: Users rely on "press Enter to accept the default". If the default is invalid, the prompt fails confusingly. Changing defaults is a zero-risk data fix vs expanding the options list, which implies curating a new canonical list.

**Alternatives considered**:
- *Expand options lists to include the offered defaults.* Rejected: "fiction" and "narrative" are so generic that they water down the options. Also makes two lists drift from each other over time.

---

## R6 — Preventing the double language prompt in `world new`

**Decision**: Audit `cli/world.rb`'s interactive flow once. The spec reports the user being asked "what language" twice. Likely cause: one ask for primary content language, a second for "output translations" language using the same question text. Fix by: (a) distinguishing prompts with different wording, or (b) asking only once and deriving defaults for the other. Default to (b).

**Rationale**: A single language choice is enough for 99% of worlds; translations are a separate opt-in. Reducing prompts speeds onboarding and matches SC-006.

**Alternatives considered**:
- *Leave two prompts but reword them.* Rejected: still slower; the second answer almost always duplicates the first.

## R7 — Seed extractor design

**Decision**: A new file `lib/eidos/seed_extractor.rb` with one class `Eidos::SeedExtractor`. Constructor: `SeedExtractor.new(llm_service:, story_bible:)`. One public method: `#extract(premise:) → SeedResult` (`SeedResult` is a small struct: `characters: [...], locations: [...], facts: [...], warnings: [...]`).

Prompt: single short prompt asking the LLM for up to ~3 candidate characters, ~2 locations, and ~3 facts derived from the premise, in strict JSON. Entries get written to the Story Bible with `origin: "seed"` and `origin_note: "derived from premise"`. Errors → empty `SeedResult` + warning; never raise.

Under `MOCK_AI=true`, `mock_responses.yml` gets a deterministic seed-extractor entry so tests are reproducible.

**Rationale**: Matches the clarification-Q2 contract. Uses `LLMService` for DI (Principle III) and the same abstraction layer as other AI calls (Principle VI). Keeps the failure mode non-fatal (FR-016). Small surface, one responsibility.

**Alternatives considered**:
- *Extend `ChapterGenerator` to do seed extraction.* Rejected: violates single-responsibility and would need a "we're seeding, not generating" mode.
- *Inline the extraction in `cli/world.rb`.* Rejected: not unit-testable without driving the whole Thor command; Constitution I is best served by a standalone class.

## R9 — Cleanup of `worlds/one-review-man/data/world.yml` and `story_facts.yml`

**Decision**: One-shot manual cleanup performed as part of this PR, not runtime code. Steps:
1. Diff current `data/story_bible/` against `data/world.yml` + `data/story_facts.yml` to confirm the bible has everything (or reconcile by hand).
2. Delete `data/world.yml` and `data/story_facts.yml` from the working tree.
3. Commit the deletion with a clear message linking to this spec.
4. Verify: `eidos produce chapter` on the one-review-man world still works (in `MOCK_AI=true`).

**Rationale**: Clarification Q3 — Eidos does not carry runtime migration code. The single real-world dual-state case is repaired as data, not as ongoing behavior.

**Alternatives considered**:
- *Add a `eidos world migrate` command for the cleanup.* Rejected: YAGNI — one world, one-time operation, shell + git does it.

## R10 — Test layering

**Decision**: Three layers.
1. **Unit** (`spec/eidos/seed_extractor_spec.rb`, prompt-utils specs, cli/world_spec.rb cases for defaults-in-options, no double-ask). Fast, no Thor.
2. **Component** (extended `chapter_generator_spec.rb` assertions for Story-Bible-backed reads; `produce_spec.rb` fresh-world output assertions).
3. **Integration** (`spec/eidos/integration/first_run_spec.rb`): `world new --quick` on a tmp dir then `produce chapter`, driven via `Open3.capture3` under `MOCK_AI=true`, asserting output is free of the forbidden substrings from SC-001.

**Rationale**: SC-001 is a textual contract on first-run output; only an integration test covers it reliably. Unit tests catch regressions fast but can't see the full output.

**Alternatives considered**:
- *Rely on integration only.* Rejected: slow feedback loop; no pinpoint diagnostics.
- *Rely on unit only.* Rejected: SC-001 cannot be asserted without the full stdout.

---

## R11 — Test suite continuity

**Decision**: Run `MOCK_AI=true bundle exec rspec` after each batch of code changes. Starting baseline is 544 examples passing. Any example that deliberately exercised the old auto-migration path is updated (not deleted) to assert the new behavior (no migration emitted, StoryBible used as source).

**Rationale**: Constitution I. Green CI throughout, no drift, no end-of-branch scramble.

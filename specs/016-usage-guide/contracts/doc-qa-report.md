# Contract: Doc-QA Report Format

**Owner**: Doc-QA agent (`.claude/agents/doc-qa.md`)
**Consumers**: human maintainers (primary), pre-commit hooks (secondary), future CI automation (tertiary).

This contract defines the exact Markdown shape of doc-qa's output. Agents and tools downstream of doc-qa rely on the structure below; deviations are a contract violation, not a stylistic choice.

---

## Required structure

```markdown
# Doc-QA Report

**Pitch**: <pitch path>
**Guide**: <guide path>
**Mode**: default

## Tier 1 — Vision Alignment

[<status>] <finding line 1>
[<status>] <finding line 2>
…

## Tier 2 — Internal Consistency

[<status>] <finding line 1>
…

## Tier 3 — Pitch Self-Consistency

[<status>] <finding line 1>
…

## Verdict

<PASS | FAIL — <N> Tier-1 failures, <M> Tier-2 failures, <K> Tier-3 failures>

## Root-Cause Candidates

- <one bullet per best-guess root cause; omit section if Verdict is PASS>
```

Where `<status>` is one of `PASS` or `FAIL`.

---

## Finding-line shape

Every finding line MUST follow one of two shapes.

**PASS shape** (one line, no continuation):

```
[PASS] <plain-prose description of what was checked>
```

Example: `[PASS] Guide glossary defines "piece" consistently with pitch §"How to think about Eidos".`

**FAIL shape** (multi-line, indented continuation):

```
[FAIL] <one-line summary>
       <indented detail line, ≥1>
       reason: <one-line explanation>
```

Continuation lines MUST be indented with exactly seven spaces (matching the `[FAIL] ` prefix width). The final continuation line MUST start with `reason:` and contain a one-sentence root-cause hypothesis.

**FAIL example** (Tier 1):

```
[FAIL] guide §"Generating a chapter book" contradicts pitch §"What Eidos is *not*"
       guide line 412: "...your storyworld becomes a publishable novel..."
       pitch line 87: "Eidos is not a chapter-only book generator..."
       reason: the guide section assumes book/chapter as the primary deliverable; the pitch's non-goals exclude this framing.
```

---

## Header rules

- The `**Pitch**:` and `**Guide**:` lines MUST contain absolute or repo-relative paths (matching the agent's input arguments).
- The `**Mode**:` line MUST be present and MUST be `default` (doc-qa has only one mode).

---

## Tier rules

- All three tier headings (`Tier 1 — Vision Alignment`, `Tier 2 — Internal Consistency`, `Tier 3 — Pitch Self-Consistency`) MUST be present, in this order, even if a tier produces zero findings. An empty tier MUST contain a single `[PASS]` line: `[PASS] No findings.`
- Tiers MUST NOT be reordered or renamed.
- Tier numbering matches `spec.md`'s FR-DQ-004 exactly.

---

## Verdict rules

- Verdict MUST be a single line beginning with `PASS` or `FAIL`.
- A `PASS` verdict means zero `[FAIL]` findings across all three tiers.
- A `FAIL` verdict MUST be followed by the count of failures per tier (Tier-1, Tier-2, Tier-3) using the literal phrase `— <N> Tier-1 failures, <M> Tier-2 failures, <K> Tier-3 failures`. Zeros are spelled out (`0 Tier-2 failures`), not omitted.

---

## Root-Cause Candidates rules

- Section MUST be present if and only if Verdict is `FAIL`.
- Each candidate is a single-bullet line stating a likely root cause in plain prose.
- Examples: `- Pitch was edited to add a new non-goal; guide section §"X" wasn't updated.` or `- Guide author drafted §"Y" before the pitch's framing was finalized.`

---

## Hard rules (binding the agent)

These are properties of the agent's behavior, not of the report — but they manifest in the report:

1. The agent MUST cite *literal* quoted text from each document for every FAIL finding. Paraphrased quotes are a contract violation.
2. The agent MUST cite line numbers reflecting the current document state (the version at run time).
3. The agent MUST NOT modify either document.
4. The agent MUST NOT name specific feature areas (e.g., "chapters," "translation," "publishing") in any prose generated by the *agent itself outside of literal quotes from the input documents*. This is the SC-011 / FR-DQ-003 hardline: the agent's prose is generic ("guide §X frames the project around the deliverable named in line N…"), and the specifics come exclusively from the documents being compared.

A grep for hardcoded feature tokens in `.claude/agents/doc-qa.md`'s instruction text MUST produce zero matches outside literal quoted-input examples. (See research D-011.)

---

## PASS example (compact, all-PASS)

```markdown
# Doc-QA Report

**Pitch**: docs/pitch.md
**Guide**: docs/usage-guide.md
**Mode**: default

## Tier 1 — Vision Alignment

[PASS] Every guide top-level section is consistent with the pitch's framing.

## Tier 2 — Internal Consistency

[PASS] No contradictions detected across guide sections.

## Tier 3 — Pitch Self-Consistency

[PASS] Pitch sections do not contradict each other.

## Verdict

PASS
```

---

## FAIL example (worked Tier-1 case)

```markdown
# Doc-QA Report

**Pitch**: docs/pitch.md
**Guide**: docs/usage-guide.md
**Mode**: default

## Tier 1 — Vision Alignment

[PASS] "Get oriented" section's mental model matches the pitch's "How to think about Eidos".
[FAIL] guide §"Generate your novel" contradicts pitch §"What Eidos is *not*"
       guide line 412: "…export your world as a finished novel manuscript…"
       pitch line 87: "Eidos is not a novel-writing tool; it produces pieces from an evolving canon."
       reason: the guide section frames a single linear novel as the deliverable, which the pitch's non-goals explicitly rule out.

## Tier 2 — Internal Consistency

[PASS] No contradictions detected across guide sections.

## Tier 3 — Pitch Self-Consistency

[PASS] Pitch sections do not contradict each other.

## Verdict

FAIL — 1 Tier-1 failure, 0 Tier-2 failures, 0 Tier-3 failures.

## Root-Cause Candidates

- Guide §"Generate your novel" was likely drafted from an earlier project framing; the pitch's IP-first stance has not propagated.
- The author of the guide section may have reused boilerplate from a previous tool's documentation.
```
